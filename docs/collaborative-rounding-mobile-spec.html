1Context, Problems, & Strategic Value

Current state

  • Rigid single-user mobile architecture. Currently, two people cannot be in a single round together at all on mobile.
  • Operational workaround. Mobile auditors must complete entirely separate, duplicate rounds for a single patient evaluation or environmental audit.
  • Intentional web concurrency. In contrast to mobile, the web application deliberately supports simultaneous multi-contributor editing. This represents the ultimate future state intended for mobile.

The problems we are solving

  • Duplicate rounds and data bloat. Forcing separate records triggers a massive surge in total system data volume, skewing analytics and inflating storage.
  • Inflated rounding time. Documenting the exact same room or unit multiple times pulls highly paid clinical leaders away from patient care.
  • Fragmented data with no master record. Audit data is shattered across multiple disparate files, meaning critical safety defects, infection vectors, or compliance failures are easily missed.
  • Severe staff frustration from lack of visibility. Auditors walk down hospital hallways blind, with zero visibility into adjacent team members’ work, leading them to frequently re-inspect areas a colleague literally just checked minutes prior.
  • Destructive overwriting. If clinicians try to bypass the system by sharing credentials or opening the same round simultaneously, the app’s native auto-save-on-exit mechanism silently erases and overwrites each other’s work.
  • Compliance audit vulnerabilities. Fragmented duplicate rounds break the continuous audit trail, leaving healthcare facilities exposed to major citations during regulatory accreditation safety audits.

Why it is important & what else this solves

  • Instant actionable insights. A single collaborative submission generates a unified, immediate work-order request list for hospital repairs or infection-control remediation.
  • Frictionless shift handoffs. If a clinician is interrupted by a medical emergency mid-round, a colleague can step into the exact same round five minutes later, view what has already been done, and seamlessly finish it.

2Summary of Strategic Decisions: Cutting the V1 Scope to 80%

To execute this feature efficiently without forcing an application rebuild, the product team has cut the V1 scope to a lean 80% roadmap by establishing four core engineering guardrails.

1. 100% script-configured toggle

All collaborative logic is locked behind a script configuration flag (collaborative_rounding_enabled = true). If a script has this setting turned off, the app runs its legacy single-user path, entirely isolating development risk. If the setting is off, no changes whatsoever are made to the UI.

2. Context-specific isolation

Round statuses are bound strictly to a matching Patient_ID + Script_ID composite pairing. A patient marked “In-Progress” in the EOC script remains completely unlocked, clear, and default for users opening the Wound Care script.

3. The heartbeat safety lock

Concurrency is solved at the entry gate, not via code merging. Only one device can actively edit a specific script round at any given second. Active users maintain a 30-second silent heartbeat. Inactivity triggers an automatic 5-minute server lockout lease release.

4. Question-level attribution

Answer objects remain untouched shared assets. Attribution metadata (modified_by_user_id and modified_timestamp) is written exclusively to the parent question row in the newly migrated SQLite foundation.

3Developer Concern Matrix: V1 Decisions, Workflows & Backend Requirements

Part 1 — “Must Decide Now” (Core Blockers)

1

What happens when two people answer at the same time?

Backend: Yes
The decision

Strict single-user check-in / check-out lockout. Concurrent editing inside the exact same script session is blocked on mobile.

The workflow

When User A opens the script, the server locks it. If User B views the patient list, the Round button is greyed out and disabled. Tapping it blocks entry and displays the native alert message:

Native alert copy “Round in Progress — [Clinician Name] is currently completing this round. This patient will unlock automatically 5 minutes after they exit or become inactive.”
Backend team updates — Yes

Build a lightweight locking table (patient_id + script_id + locked_by_user_id + last_heartbeat_timestamp). Expose POST /rounds/{id}/lock, POST /rounds/{id}/heartbeat (accepting 30-second pings), and POST /rounds/{id}/unlock endpoints. Implement a background cron job running every 30–60 seconds that purges locks whose last heartbeat is older than 5 minutes.

1b

What happens if multiple rounders are actively concurrent on web, and then switch over to mobile? (Scenario edge case)

Backend: Yes
The decision

Immediate filter into mobile single-checkout rule. Multi-user data generated on web remains safe, but mobile entry is serialized.

The workflow

The Carenode server processes and saves multiple web contributors to the master draft. When clinicians switch to mobile, the patient list parses the draft and immediately renders the two-person icon and the “In-Progress” badge. The first clinician to tap the active Round button secures the exclusive server lock, wipes their local script cache, and downloads the full web-generated data into local SQLite. Clinicians 2 and 3 are blocked by the disabled, locked Round button workflow.

Backend team updates — Yes

Ensure the draft response payload (GET /rounds/{id}/draft) aggregates all open answer records contributed on web across multiple users into a clean, unified JSON structure that mobile SQLite can ingest upon opening.

1c

What if one user keeps rounding on web while another user attempts to round on mobile? (Cross-platform edge case)

Backend: Yes
The decision

Platform-aware asymmetric lockout. Preserve web’s intentional multi-user environment while shielding mobile via mutual exclusion.

The workflow
If web is active first

While users are actively editing on web, the server state reflects active web editors; the mobile patient list receives is_locked = true, turning the Round button into its greyed-out state with the alert:

Mobile alert copy “Round in Progress on Web — Please wait for web editors to finish before opening on mobile.”
If mobile is active first

Mobile holds exclusive write access, and any web user opening the round sees a blocking banner:

Web banner copy “A clinician is currently updating this round on mobile. Web editing will be available once they complete their handoff.”
Backend team updates — Yes

Integrate web sessions into the server locking logic. When a web user opens a collaborative round, register a web session/heartbeat so the backend knows web_editors_active = true. If mobile holds the lock, return a 423 Locked status to web so web can display the blocking banner.

2

How fresh does the round have to be?

Backend: Yes
The decision

Fetch on open / manual refresh only. Zero background polling or WebSocket overhead.

The workflow

The mobile app will never poll the server in the background. It reads the lock state and active draft answers strictly when the patient list view initializes, or when the user executes a manual pull-to-refresh.

Backend team updates — Yes

Optimize GET /patients (or the existing patient list endpoint) to return lightweight is_locked and is_collaborative boolean flags per patient for the requested Script_ID without executing slow, deep database queries.

3

Does a round update while it’s open in front of you?

Backend: No
The decision

No live UI updates. Frozen local UI state.

The workflow

Once a round is successfully opened via an active server lock, it remains a frozen snapshot. Content will never shift or disappear while open. New data from other users is only rendered if the screen is backed out and re-entered.

Backend team updates — No

Backend does not need to push live WebSocket events or change in-flight streaming payloads. The standard REST request-response cycle is maintained.

4

Who is allowed to clear, abandon, or even access a shared round?

Backend: Yes
The decision

Shade out destructive actions and block with explicit toast messaging.

The workflow

The moment collaborative_rounding_enabled = true is active on a script, the mobile client shades out and disables the “Clear All” button. Tapping it displays:

Toast copy “collaborative rounds cannot be cleared”

Backing out releases the lock safely without deleting server drafts.

Backend team updates — Yes

Add a server-side guardrail on DELETE or bulk-clear endpoints rejecting any clear request if the round’s script configuration has collaborative_rounding_enabled = true (returning 403 Forbidden).

5

Who possesses submission authority? (Multi-user role gate)

Backend: Yes
The decision

Permission-gated submission actions.

The workflow

The mobile client evaluates user credentials. The “Submit” button will be completely shaded out and disabled unless the rounder possesses explicit Submitter permissions. Non-submitters can save and close, but cannot execute the final submission call.

Backend team updates — Yes

Return the can_submit_rounds (or equivalent role permission) boolean flag within the user authentication/session payload, and enforce this permission server-side upon receiving POST /rounds/{id}/submit.

6

Who gets credit? (Badges, reporting, and My Rounds filters)

Backend: Yes
The decision

Final submitter wins primary credit; creators, contributors, and submitters explicitly tracked.

The workflow

Compliance badges and “My Rounds” dashboard filters are awarded to the clinician who hits the final “Submit” button. However, individual text blocks and question rows retain permanent metadata tracking in audit logs.

Backend team updates — Yes

Store created_by_user_id and submitted_by_user_id on the parent Rounds table. For badge award and compliance aggregation jobs, count rounds under submitted_by_user_id, while maintaining granular contributor IDs in relational response tables for compliance auditing.

7

Can a collaborative round be done offline?

Backend: Yes
The decision

Hybrid connection rule — creator immunity vs. contributor Wi-Fi lock.

The workflow
Fresh creator

Offline allowed using the standard active Round button; saves to local SQLite and pushes when online.

Contributor

Wi-Fi is mandatory to enter and secure the server lock. If the connection drops mid-round for more than 5 minutes, the lock breaks on the server; upon reconnecting, a lock eviction check flips the screen to read-only mode if another user claimed the lock.

Backend team updates — Yes

Expose a fast GET /rounds/{id}/lock-status validation check so mobile can verify whether its lock lease is still intact upon reconnecting, before flushing queued SQLite data.

8

What about photos and voice recordings?

Backend: Yes
The decision

Local-first capture, cloud upload-on-close, inherited attribution. No voice recording in V1. Existing 10-photo UI preserved.

The workflow

Clinicians use the existing UI (up to 10 photos per option). Photos save locally to disk. On auto-save/exit, a background queue flushes images to AWS S3. The 5-minute heartbeat lock will not release until all images finish uploading. The next auditor pulls image URLs from the server dynamically. Photos inherit parent question attribution.

Backend team updates — Yes

Provide direct pre-signed S3 upload URLs, or an endpoint to receive multi-image payloads per question response, and store the resulting public/secured S3 image URLs in the draft response JSON.

10

Capture attribution everywhere from day one (rebuilding how answers are stored)

Backend: Yes
The decision

Question-level metadata tracking. Answer choices remain untouched shared assets. No individual checkbox tracking in V1.

The workflow

Developers append modified_by_user_id and modified_timestamp to the SQLite Patient_Responses table.

  • Multi-select / checklists: last touch wins.
  • Free text: append-only UI threads — User A’s text is locked in a read-only bubble, and User B gets a fresh input box below.
Backend team updates — Yes

Update the response persistence schema to accept modified_by_user_id and modified_timestamp at the question level. For free text, support an append-array/child table (Response_Text_Blocks) so multiple narrative entries with individual timestamps and author IDs can be stored and returned per question.

Part 2 — Existing Behaviors That Must Change in V1

B1

In-progress rounds must be fetched repeatedly, not once at login.

Backend: Yes
The decision

Targeted fetch on open.

The workflow

Plumbing is added to trigger a GET /rounds/{id}/draft call the exact moment a clinician taps the active Round button to open a collaborative script.

Backend team updates — Yes

Ensure the GET /rounds/{id}/draft endpoint returns the latest draft state efficiently for the requested Script_ID with minimal latency.

B2

The app must accept updates to a round it already has (ignores server versions).

Backend: No
The decision

Wipe-and-populate local script cache.

The workflow

Because mobile is now on a modern SQLite layer, when a collaborative script is opened, the local database clears its local cache for that specific script context only, and cleanly populates it with the server’s fresh JSON draft state.

Backend team updates — No

The standard draft response payload is consumed; cache wiping and repopulation is handled entirely client-side by the mobile SQLite data layer.

B3

The rounding list “in progress” state must come from the server.

Backend: Yes
The decision

Script-isolated “In-Progress” status capsule.

The workflow

An “In-Progress” status capsule displays on the patient list anytime a round has been started. It is strictly script-specific: if User A starts a round on Script 1, the patient says “In-Progress” only for that script. Toggling to Script 2 clears the “In-Progress” badge.

Backend team updates — Yes

Update the patient list API query to join active drafts against the specific Script_ID passed in the request header/query parameter, returning is_in_progress = true only when an open draft exists for that script.

B4

The rounding list will visibly move, causing screen flicker while scrolling.

Backend: No
The decision

Frozen scroll rows.

The workflow

To protect list stability, rows on the mobile patient list screen will never move or reorder dynamically due to background events. Rows remain entirely locked in place until a user forces a manual pull-to-refresh.

Backend team updates — No

Entirely a client-side UI rendering rule; the mobile app freezes list sorting order while scrolling.

B5

Submitted rounds need to show a submitter plus contributors everywhere a round’s author appears today.

Backend: Yes
The decision

Read-only array parsing.

The workflow

If a round was completed on web with complex history, the Carenode backend serves this as a flat, pre-parsed JSON array. The mobile historical review screen runs a standard UI loop to render checkboxes with attribution capsules seamlessly.

Backend team updates — Yes

Update GET /rounds/{id}/summary (the historical completed round endpoint) to aggregate and return creator, submitter, and unique contributor arrays alongside question-level attribution metadata.

B5b

Pull-to-refresh on the rounding list currently does not refresh in-progress rounds.

Backend: Yes
The decision

Universal pull-to-refresh synchronization.

The workflow

The manual pull-to-refresh action on the patient list is refactored to fetch both unstarted and in-progress collaborative states simultaneously.

Backend team updates — Yes

Support query execution on the main list API that checks for active locking states and multi-user draft modifications dynamically upon request.

B6

Existing in-progress rounds at the moment of upgrade need a defined outcome.

Backend: No
The decision

Clean discard of legacy in-progress drafts on migration update.

The workflow

The exact millisecond a user installs the new mobile build, any unsubmitted local drafts matching the upgraded collaborative script schema are cleanly deleted from the local SQLite database to prevent schema collision.

Backend team updates — No

Handled entirely on the mobile device during the post-install SQLite database initialization script. Backend data for already-submitted rounds is 100% untouched.

Risk isolation reminder

Every behavior in this brief is gated by collaborative_rounding_enabled. Scripts with the flag off run the legacy single-user path with no UI change whatsoever, which keeps the V1 blast radius limited to opted-in scripts.
